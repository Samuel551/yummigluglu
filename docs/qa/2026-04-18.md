### Top 5 más urgentes

1. Webhook RevenueCat confía en `app_user_id` del body sin validar firma HMAC → suplantación de suscripción si se filtra el secret.
2. `usePlanStore.cargarPlan` deja `recetasCache = {}` cuando carga un plan existente (el helper privado corre sólo a veces) → UI muestra guiones `—` en todos los días.
3. Panel admin confía sólo en `useAdminStore.autenticado` para navegación — la fuente real son las policies, pero el usuario registrado como `es_admin()` puede quedar autenticado hasta reinicio → cualquiera con la contraseña admin tiene edit completo aunque luego sea removido del array de admins.
4. `(tabs)/_layout.tsx` dispara `cargarFavoritos()` antes de `cargarPerfiles()` — sin dependencia — y sin re-ejecutar cuando vuelve la sesión.
5. `registrar_primer_admin` queda expuesto: cualquier usuario autenticado puede registrarse como admin si la tabla está vacía, sin verificación de email/dominio/rol → en ambiente dev con muchos testers, el primer tester se vuelve admin.

## Hallazgos Detallados

### CRÍTICOS

#### C1. Webhook RevenueCat — sin validación de firma y `app_user_id` no auditado

- **Archivo:** `supabase/functions/revenuecat-webhook/index.ts:31-48`
- **Problema:** La validación es un shared secret simple (`Authorization` header). No hay HMAC-SHA256 sobre el body. Si el secret se filtra (logs, dashboards, repo), cualquiera puede mandar un POST con `app_user_id: "<cualquier-uuid>"` y activar premium para ese user.
- **Adicional:** `event.id` se guarda en `revenuecat_customer_id`, pero no se verifica que `app_user_id` corresponda a un usuario real de `auth.users`. Un evento mal formado puede crear filas huérfanas.
- **Impacto:** Bypass de pago + filas basura en `suscripciones`.
- **Solución:**

```ts
// Validar firma HMAC (RevenueCat manda X-RevenueCat-Signature si está configurado)
const rawBody = await req.text();
const signature = req.headers.get('x-revenuecat-signature');
const expected = await computeHmac(rawBody, WEBHOOK_SECRET);
if (!signature || !timingSafeEqual(signature, expected)) {
  return new Response('Unauthorized', { status: 401 });
}
const payload = JSON.parse(rawBody);

// Verificar que el user exista antes de upsert
const { data: user } = await supabase.auth.admin.getUserById(userId);
if (!user) return new Response('Usuario desconocido', { status: 404 });
```

#### C2. `cargarPlan` no repuebla `recetasCache` de forma robusta

- **Archivo:** `store/usePlanStore.ts:125-148`
- **Problema:** Cuando existe un plan en DB, `cargarPlan` intenta llamar `_cachearRecetasDePlan` via `as` casting sucio. Si el store se monta antes del cast (p.ej. hot reload), el helper no corre y `recetasCache` queda `{}`. Consecuencia: `plan.tsx` renderiza guión `—` en cada slot aunque el plan esté bien cargado.
- **Repro:** abrir Plan tab, hot-reload, navegar de nuevo.
- **Solución:** definir el helper como método normal de la interface en vez del truco `as`. Mover dentro del store oficialmente:

```ts
interface PlanState {
  // ...
  _cachearRecetasDePlan: (dias: DiasPlan) => Promise<void>;
}
// y en cargarPlan:
await get()._cachearRecetasDePlan(data.dias);
```

### ALTOS

#### A1. `registrar_primer_admin()` es auto-servicio abierto

- **Archivo:** `supabase/migrations/003_admin_panel.sql:30-42`
- **Problema:** Cualquier autenticado puede llamar `registrar_primer_admin()` y, si la tabla está vacía, se vuelve admin. En un ambiente con varios testers (QA, beta testers), el primero gana.
- **Mitigación recomendada:** remover la función una vez registrado el admin inicial, o restringir a un email hardcodeado:

```sql
CREATE OR REPLACE FUNCTION registrar_primer_admin() ...
BEGIN
  IF (SELECT email FROM auth.users WHERE id = auth.uid()) != 'a.montero.g98@gmail.com' THEN
    RETURN FALSE;
  END IF;
  -- resto igual
END;
```

#### A2. Race condition en `(tabs)/_layout.tsx` — favoritos antes de perfil

- **Archivo:** `app/(tabs)/_layout.tsx:34-38`
- **Problema:**

```tsx
useEffect(() => {
  if (!session) return;
  cargarPerfiles().finally(() => setPerfilesCargados(true));
  cargarFavoritos(); // corre en paralelo, sin perfilActivo
}, [session, cargarPerfiles, cargarFavoritos]);
```

- **Impacto:** Si más adelante los favoritos se filtran por `perfil_id`, este orden rompe. Ya hoy desperdicia una round-trip cuando el user cambia de perfil.
- **Solución:** encadenar o separar efectos.

```tsx
useEffect(() => {
  if (!session) return;
  cargarPerfiles().finally(() => setPerfilesCargados(true));
}, [session]);
useEffect(() => {
  if (!perfilActivo) return;
  cargarFavoritos();
}, [perfilActivo?.id]);
```

#### A3. Hash admin expuesto (heredado) — falta defensa en profundidad

- **Archivo:** `store/useAdminStore.ts:3` y `EXPO_PUBLIC_ADMIN_PASSWORD_HASH`
- **Problema:** Cualquier atacante con el APK extrae el hash SHA-256 sin salt y hace fuerza bruta offline. La DB ya tiene RLS via `es_admin()`, pero el screen `admin/index.tsx` hace `supabase.rpc('registrar_primer_admin')` que no depende del hash.
- **Mitigación:** (1) usar contraseña ≥ 32 chars random, (2) agregar salt (PBKDF2 con iterations ≥ 100k), (3) considerar reemplazar por login específico admin con `supabase.auth` + verificación `es_admin()`.

#### A4. `useEffect` con dependencias incompletas en `plan.tsx`

- **Archivo:** `app/(tabs)/plan.tsx:274-281`
- **Problema:**

```tsx
useEffect(() => {
  limpiarPlan();
}, [perfilActivo?.id]); // falta limpiarPlan
useEffect(() => {
  if (!perfilActivo) return;
  cargarPlan(perfilActivo.id, inicio);
}, [perfilActivo?.id, inicio]); // falta cargarPlan
```

ESLint `react-hooks/exhaustive-deps` lo avisa. Funciona de pedo porque los métodos zustand son estables.

- **Solución:** agregarlos o añadir `// eslint-disable-next-line` con comentario explicando por qué son estables.

#### A5. `useEffect` sin deps en `admin/index.tsx`

- **Archivo:** `app/admin/index.tsx:23-25`
- **Problema:**

```tsx
useEffect(() => {
  verificarYCargar();
}, []);
```

`verificarYCargar` captura closures viejos (no es problema hoy porque no depende de estado externo, pero es fragile). Además, si el user navega a otro screen y vuelve, no se revalida.

- **Solución:** extraer `verificarYCargar` con `useCallback([])` o mover dentro del effect.

### MEDIOS

#### M1. `useAdminStore.autenticado` no persiste ni expira

- **Archivo:** `store/useAdminStore.ts`
- **Problema:** Si se mata la app, hay que reingresar la contraseña. OK. Pero si se deja abierta, el acceso queda indefinido. Sin auto-logout tras N minutos.
- **Solución:** guardar `autenticado_hasta: timestamp` con TTL de 30 min.

#### M2. `generarDiasPlan` — pool vacío no se loguea

- **Archivo:** `store/usePlanStore.ts:80-82`
- **Problema:** Si no hay recetas para un momento del día (p.ej. no hay snacks compatibles con la etapa), se pone `null` en silencio. Al usuario le aparece `—`. No hay forma de distinguir "bug en catálogo" vs "decisión del generador".
- **Solución:** loguear con `console.warn` y retornar un flag para que la UI muestre "Faltan snacks en el catálogo".

#### M3. Mensajes de error genéricos en `usePlanStore`, `useSuscripcionStore`, `useRecetasStore`, `useFavoritosStore`

- **Problema:** Siguen propagando `error.message` crudo (`JWT expired`, `row-level security policy`) al usuario.
- **Solución:** migrar a `mensajeError(e)` de `lib/errores.ts` como ya hicieron en `useAuthStore` y `useDiarioStore`.

#### M4. `admin/recetas.tsx` — cast sucio `Receta[]` sobre un SELECT parcial

- **Archivo:** `app/admin/recetas.tsx:36-41`
- **Problema:** El SELECT trae sólo 7 columnas pero el cast dice `Receta[]`. TypeScript no chequea y el render usa solo campos que están, pero si alguien agrega un campo obligatorio a `Receta`, el bug compila.
- **Solución:** tipo local `type RecetaAdminLista = Pick<Receta, 'id' | 'slug' | 'nombre' | 'activa' | 'es_premium' | 'video_url' | 'etapas_compatibles' | 'tiempo_preparacion'>;`

#### M5. Register — `limpiarError` no se llama al escribir password/confirm

- **Archivo:** `app/(auth)/register.tsx:120-148`
- **Problema:** Sólo el input de email limpia el error. Si el user tipea y cambia la contraseña, el banner rojo sigue visible.
- **Solución:** `onChangeText={(v) => { setPassword(v); limpiarError(); }}` en los 3 inputs.

#### M6. Onboarding — sin feedback si `crearPerfil` falla silenciosamente

- **Archivo:** `app/onboarding.tsx:97-110`
- **Problema:** `crear()` hace `router.replace` solo si `perfil` llega no-null, pero si `crearPerfil` falla (`perfiles.length >= 2`, insert falla), el user se queda en el paso 3 sin saber qué pasó. El `error` se renderiza al fondo pero el scroll puede estar arriba.
- **Solución:** `scrollRef.current?.scrollToEnd()` cuando `error` cambie, o mostrar `Alert.alert`.
